\section{Experiments}
\label{sec:experiments}
So far, we have only looked at the three methods mathematically (and observe what \emph{could} make Method B and C faster) and we want to see the actual result that depends on document and queries.

% The calculations tell us what \emph{could} make Bitplanes or Backward Walk faster, but the actual result depends on the documents, the queries, and how much work each method ends up doing.

So the experiment is simple:

\textbf{For the same search problem and the same recall requirement, what is the fastest configuration I can find for A, B and C?}

Each method is allowed to choose the parameters that "make sense for it".

Method A can choose its cluster count and how many clusters to open.

Method B can choose those same cluster settings, together with its leaf size and node budget.

Method C can choose the cluster settings, starting prefix depth and stopping rule.


Note: B and C do not necessarily work best with the same cluster layout as A. For example, Bitplanes may be able to open a much larger group of documents and then remove most of them before the "query-document dot product" operation.

I use two collections:

Quora & Qwen3 0.6B & 522,931 & 1,000 & 32, 256, 1024\\\bottomrule
\end{tabular}
\end{center}
The document and query embeddings are generated before the search experiment begins.

The timer therefore measures only the part of the pipeline that I am trying to improve:

Embedding generation and the later full-vector reranking stage are not included.

For one comparison, A, B and C use:
\begin{itemize}\setlength{\itemsep}{1pt}
\item the same documents;
\item the same 1,000 queries;
\item the same binary dimension;
\item the same scoring function;
\item the same requested result count $K$;
\item the same exact reference answers.
\end{itemize}
The idea is simply: \textbf{same search problem, different way of searching it.}

Changing the binary dimension is treated as a different comparison because, for example, a 32-bit binary vector and a 256-bit binary vector do not necessarily rank the documents in the same order.

\subsection{How the comparison works}
Before testing approximate search, I first calculate the exact answer for every query.

I do this by performing a scoring operation for every document in the collection using the same binary scoring function used by A, B and C.

Suppose the exact top five document IDs are \texttt{[12, 7, 91, 4, 30]} and one method returns \texttt{[12, 7, 91, 4, 85]}.

Four of the five correct IDs were recovered, so:
\[
\mathrm{Recall@5}=80\%.
\]
I repeat this over all 1,000 queries.

Therefore, in this document, if it's written as \textbf{99\% recall}, we mean that the method recovers 99\% of the exact binary top-$K$ document IDs on average.

\Needspace{4\baselineskip}
\textbf{Choosing the parameters}\par
For every method, we try multiple configurations.

For A:
\begin{itemize}\setlength{\itemsep}{1pt}
\item number of clusters $C$;
\item number of opened clusters $P$.
\end{itemize}
For B:
\begin{itemize}\setlength{\itemsep}{1pt}
\item $C$;
\item $P$;
\item leaf size;
\item node budget.
\end{itemize}
For C:
\begin{itemize}\setlength{\itemsep}{1pt}
\item $C$;
\item $P$;
\item starting prefix depth;
\item stopping rule.
\end{itemize}
For a given recall target, such as 80\%, 90\%, 95\%, 99\%, I discard configurations that do not reach that recall.

Among the remaining configurations, I keep the fastest one for each method.

So the comparison is:

\subsection{Main result}
Let's first look at Qwen with 32-bit binary documents while returning one result: $K=1$.

This is the setting where the difference between the three search strategies is the clearest.
\begin{center}\small

80\% & 0.0308 ms & \textbf{0.0295 ms} & 0.0318 ms\\
90\% & 0.0498 ms & \textbf{0.0432 ms} & 0.0497 ms\\
95\% & 0.0805 ms & \textbf{0.0520 ms} & 0.0799 ms\\
99\% & 0.1948 ms & \textbf{0.0809 ms} & 0.1688 ms\\\bottomrule

At the 99\% recall target, Bitplanes take $0.0809$ ms compared with $0.1948$ ms for A.

So in this setting, B is approximately $2.4\times$ faster than the original method.

\subsection{Why is Bitplanes faster?}

let's look at the recall 99\% settings chosen by each method.
\begin{center}\small
\begin{tabularx}{\linewidth}{@{}lrrYrr@{}}\toprule
Method & Clusters & Clusters opened & Search setting & Recall & Time (ms)\\\midrule
A & 4096 & 180 & Scan & 99.0\% & 0.1948\\
B & 16 & 9 & Leaf 128, budget 8192 & 99.2\% & 0.0809\\
C & 1024 & 78 & Start depth 4, exact stop & 99.0\% & 0.1688\\\bottomrule
\end{tabularx}
\end{center}

The first interesting thing is that the methods choose very different cluster layouts.

Now we can also observe how many documents reach the search stage and how many of them undergo a "query-document dot product" operation:
\begin{center}\small
\begin{tabular}{@{}lrr@{}}\toprule
Method & Documents inside opened clusters & \shortstack{Scoring\\operations}\\\midrule
A & 24,181 & 24,181\\
B & 295,031 & 818\\
C & 41,147 & 26,153\\\bottomrule
\end{tabular}
\end{center}
We can observe the following:

\textbf{Method A}\par
A uses very selective cluster selection:
\[
\text{select clusters}\ \to\ 24{,}181\text{ documents}\ \to\ 24{,}181\text{ scoring operations}.
\]
\textbf{Method B}\par
B does almost the opposite:
\[
\begin{aligned}
&\text{select much larger clusters}\ \to\ 295{,}031\text{ documents}\\
&\hspace{35mm}\downarrow\ \text{Bitplanes}\\
&\hspace{35mm}818\text{ "query-document dot product" operations}.
\end{aligned}
\]
B therefore performs scoring operations for only
\[
818/295031\approx0.28\%
\]
of the documents inside its opened clusters.

This is exactly the tradeoff described in Section 2. B performs extra bitmap work, but in this case that work removes so many "query-document dot product" operations that the complete query becomes faster.

Backward Walk also removes some "query-document dot product" operations:

However, the reduction is much smaller than B's. C also needs to perform prefix lookups while progressively broadening the query prefix.

At this setting, C visits around 3.5 prefix depths and performs around 495 boundary searches per query.

Its final time is $0.1688$ ms, which is better than A in this particular comparison, but still much slower than B. 

So the three methods are effectively making three different choices:
\begin{center}\small
\begin{tabularx}{\linewidth}{@{}lY@{}}\toprule
A & Reduce documents heavily during cluster selection, then perform a scoring operation for every document\\
B & Use coarse cluster selection, then aggressively prune with Bitplanes\\
C & Use medium cluster selection, then progressively broaden a prefix\\\bottomrule
\end{tabularx}
\end{center}

\subsection{Does this advantage always happen?}
TLDR: Not really. The previous result asks for only one final result: $K=1$. Now let's say, we increase the number of requested results to $K=100$.

At the 99\% binary recall target:
\begin{center}\small
\begin{tabular}{@{}lrrr@{}}\toprule
Representation & A & B & C\\\midrule
Nomic 64 & 1.915 ms & 2.071 ms & \textbf{1.875 ms}\\
Nomic 256 & \textbf{13.453 ms} & 13.866 ms & 14.645 ms\\
Nomic 768 & \textbf{45.088 ms} & 45.217 ms & 45.196 ms\\
Qwen 32 & \textbf{0.400 ms} & 0.439 ms & 0.404 ms\\
Qwen 256 & \textbf{3.564 ms} & 3.721 ms & 4.039 ms\\
Qwen 1024 & \textbf{22.863 ms} & 23.098 ms & 22.930 ms\\\bottomrule
\end{tabular}
\end{center}
In these selected settings, B performs no useful splitting and C starts from depth zero. In other words, both methods effectively fall back toward the original scan.

C's slightly lower median on Nomic64 is a scan-like timing difference; it does not come from avoiding "query-document dot product" operations.

This also makes intuitive sense. When we only need one result, B can search the most promising branches and safely ignore many alternatives.

When we need 100 results, many more branches can still contain one of the required documents. B therefore has to search much more of the tree.

Eventually, the cost of pruning is no longer worth it.

\textbf{The Bitplane advantage therefore appears strongest when $K$ is small enough that many branches can be safely ignored.}

This is a measured result for the tested settings, not a guarantee that B can never help for larger $K$.

\subsection{Summary}

For Qwen32 with one requested result, Bitplanes are clearly faster in the tested search setup.

At 99\% binary recall:
\begin{itemize}\setlength{\itemsep}{1pt}
\item A takes 0.1948 ms;
\item B takes 0.0809 ms;
\item C takes 0.1688 ms.
\end{itemize}
B is therefore about $2.4\times$ faster than A.

\textbf{Why?}.

A selects a relatively small number of documents and then performs scoring operations for all of them.

B selects a much larger number of documents, but its Bitplane search reduces roughly 295,000 opened documents to only around 818 "query-document dot product" operations.

In this setting, the "query-document dot product" work avoided is large enough to repay the extra bitmap work.

However, this does not happen everywhere. When the result count increases to $K=100$, B and C become much closer to ordinary scanning and the advantage disappears in the tested settings.

% So the result is not: \textbf{Bitplanes are always faster.}

% \textbf{"Bitplanes can be faster when the query only needs a small number of results and the query bits allow a large fraction of the opened documents to be ruled out before the leaf node's "query-document dot product" operations."}

Backward Walk shows the same general tradeoff, but in the tested data it does not reduce the scoring work as aggressively as Bitplanes.
