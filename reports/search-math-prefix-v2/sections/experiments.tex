\section{Experiments}
\subsection{Setup}
To see where each method helps, I started with 256-bit codes from two collections. I then added shorter and longer codes from the same cached embeddings. Within one setup, A, B and C receive exactly the same document codes, query vectors and reference IDs. I change the index and search settings, then compare the time needed to reach the same recall target.

\begin{center}\small
\begin{tabular}{@{}llrrl@{}}\toprule
Collection & Embedding model & Documents & Queries & Bits\\\midrule
MS MARCO & Nomic v1.5 & 1,000,000 & 1,000 & 64, 256, 768\\
Quora (BEIR) & Qwen3 0.6B & 522,931 & 1,000 & 32, 256, 1024\\\bottomrule
\end{tabular}
\end{center}
I reused the cached Nomic document embeddings and encoded a fixed random selection of 1,000 official MS MARCO development queries~\cite{msmarco,nomic}. For Quora, I encoded the complete BEIR corpus and a fixed random selection of 1,000 official test queries~\cite{beir,qwen}. Selection happened before running any search. All corpus entries are retained, including duplicate text. None of the selected Quora queries has an identical ID or text in the corpus.

Each model produces a full vector once. I take prefixes at lengths supported by its model card, normalize each prefix, and store its signs. Changing the length can change the nearest neighbors, so each length has its own reference results. I obtain those results by scoring every document with the full binary score and keeping the best 100, using document ID to resolve ties. The first one or ten IDs give the references for the smaller result counts. Human relevance labels are available in the source datasets; the recall measured here is agreement with the exhaustive binary scorer.

The machine is an Apple M5 Max with 128 GiB of memory. I use one native search query at a time and one Faiss search thread, with the same 32 GB process limit for all methods. Reported query time starts with a cached query vector and ends with the returned IDs. It includes selecting clusters and searching their documents. Embedding generation and text reranking are outside this timer. Encoding and reference preparation finish before timed searches begin.

\subsection{Parameters}
For each cluster layout, I first count how many probes are needed to include the required fraction of reference IDs. A scores every document in those clusters, so it can recover all of those opened reference IDs. I give B and C the same probe choices; their local search can still miss a result, so they may need to open more clusters to reach the target.

\begin{center}\small
\begin{tabularx}{\linewidth}{@{}lY@{}}\toprule
Parameter & First sweep\\\midrule
Number of clusters & 1, 64, 1024, 4096\\
Results returned & 1, 10, 100\\
Average recall targets & 50\%, 80\%, 90\%, 95\%, 99\%\\
Opened clusters & Probe counts derived for those targets, plus every cluster\\
B: leaf size & 128 or 2048 documents\\
B: visited-set budget & 512 or 8192; both split nodes and leaves count\\
B: random exploration & 0; visit the lowest-penalty waiting set first\\
C: starting prefix & 16 bits\\
C: candidate target & 1,000; 10,000; 100,000; half the collection; or 0\\\bottomrule
\end{tabularx}
\end{center}
For C, target zero continues to depth zero and scores every opened document. A positive target stops after a complete depth has produced enough candidates. This can exceed the requested count when the next prefix contains many documents.

The two 256-bit grids each contain 570 settings. The wider Qwen grid keeps result counts 1 and 100; the full-width Nomic comparison focuses on 100 results at 95\% and 99\% recall. These choices leave time to try different search settings instead of repeating the same grid at every width. The saved schedule states exactly what was attempted, and the results table counts only completed settings.

For the shorter codes, I also try leaves of 8 and 32 rows, extra probe counts aimed at 99.5\% routing coverage, and C starting depths 0, 1, 4, 16 and 32. B normally visits equal-penalty sets in the order they were created. I add an option to visit the deeper set first when penalties tie. This changes the visit order while keeping both branches and the same score bound. The configurations record which order each setting uses.

I use all 1,000 queries for each completed setting and keep results that miss the recall target. The next runs are divided into small batches so that one slow setting does not consume the whole allowance. I then select each method's fastest qualifying settings and repeat those choices in three fresh processes, changing the order of the runs. The whole grid is not repeated three times.

There is one comparison worth checking directly. If B scores 512 whole clusters without splitting any of them, its alternative is A with 512 probes. Comparing it only with A at a larger probe count would exaggerate the benefit. I therefore add A probe counts at apparent B or C advantages, and give C its depth-zero setting at A's selected layouts. The follow-up settings use the same arrays and queries as the first sweep.

\subsection{Code and reproduction}
The C++ scorer is shared by all three methods. A and B are in \path{cpp/index.cpp}; C is in \path{cpp/prefix_index_v2.cpp}. The Python worker in \path{experiments/prefix_batch_worker_v2.py} times routing and search, records the work counts, and compares returned IDs with the exact references.

After preparing the arrays using \path{experiments/prepare_prefix_pools_v2.py}, we can run one complete setup with this Python flow:
\begin{lstlisting}
import json
from pathlib import Path
from experiments.prefix_study_v2 import (
    prepare, run, summarize, repeat,
)

config = json.loads(Path(
    "configs/prefix-study-v2/qwen-quora-d256.json"
).read_text())
output = Path("results/my-quora-run")

prepare(config, output)  # Build cluster layouts and the schedule.
run(output)             # Measure every declared setting.
summarize(output)       # Choose settings that reach the targets.
repeat(output)          # Run those choices three more times.
\end{lstlisting}
The configurations are in \path{configs/prefix-study-v2/}. Input hashes, parameters, power settings, per-query records and repeated timings are saved under \path{results/prefix-study-2026-09-13/}. The plots come from \path{experiments/prefix_figures_v2.py}. Data acquisition and encoding commands are in \path{docs/expanded-pool-preparation.md}. The short-code schedules use \path{experiments/prefix_exploration_v2.py} to divide settings into small batches; \path{experiments/prefix_followups_v2.py} prepares the direct comparisons described above.
