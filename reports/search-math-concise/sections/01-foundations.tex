\section{What are we trying to make faster?}
A search index receives a query and returns a small set of documents. If we calculate a
score for every document, finding the best results is straightforward. The difficulty is
doing this quickly when the collection grows. We can skip documents, but then we need to
know how much work the shortcut costs and whether it skips the results we wanted.

This report compares three ways to search the same binary document embeddings. Method A
opens selected clusters and scans their documents. Method B opens clusters and splits their
documents using bitplanes. Method C opens clusters and looks up bit patterns, beginning with
the pattern preferred by the query. We will call C \emph{weighted key lookup}; it is the
concrete version of the idea of starting at the ideal answer and ``walking backwards.''

Our question has three constraints: a document count, a RAM budget, and a required recall.
Recall measures how many of the correct reference results the search recovers. We want the
lowest latency that satisfies those constraints. The number of calculations matters, but so
does the memory each calculation reads. Avoiding a document score can introduce other work.

The experiments give three different outcomes. On the tested real embeddings, neither
alternative established a speed advantage over a well-tuned scan. On constructed queries
whose important coordinates stayed in one prefix, key lookup had a small advantage over a
closely related directly routed scan. When the important coordinates changed with each
query, bitplane branching had a large advantage in the constructed case. Understanding
those conditions is more useful than declaring one method the winner everywhere.

We begin with one query and six documents, then count the work and storage for each method.
The second half explains recall, parameter selection, and the measurements. The final
calculation asks what could happen at a billion documents. Those larger latency numbers are
forecasts; the complete native indexes were tested through eight million documents.

\subsection{One query, six documents, one score}
An embedding is a vector of numbers produced from text. We keep the query vector as numbers,
but replace each document coordinate with its sign. A stored bit of 1 means $+1$; a bit of 0
means $-1$. This is \emph{binary quantization}. For the example, let
\[
q=[0.7,\ 0.5,\ -0.4,\ -0.6,\ 0.3].
\]
The score is the dot product: multiply corresponding coordinates, then add. The query would
prefer a document with signs \texttt{11001}, because every contribution would be positive.
That document scores $0.7+0.5+0.4+0.6+0.3=2.5$.

The correct top two are documents 3 and 4. We use smaller document IDs first if scores tie.
Every method will be checked against that same rule. The script
\path{examples/small_search.py} runs this example against the native implementations.

Why should query magnitude guide a branch? At coordinate 1, matching the query contributes
$+0.7$ and mismatching contributes $-0.7$. The mismatch lowers the score by $1.4$. At coordinate
5, the corresponding loss is only $0.6$. Large magnitudes therefore make expensive mistakes.
For a query with $d$ coordinates, write the total ideal score as $Q=\sum_{i=1}^{d}|q_i|$.
Writing $b_i$ for the decoded sign ($+1$ or $-1$), if the mismatching coordinates
have total magnitude $p$, then
\begin{equation}
S(q,b)=Q-2p,
\qquad p=\sum_{i:\,b_i\ne\operatorname{sign}(q_i)}|q_i|.
\label{eq:score}
\end{equation}
For document 4, only coordinate 5 mismatches: $S=2.5-2(0.3)=1.9$. We can rank by the largest
score or the smallest mismatch penalty. They give the same order. Ordinary Hamming distance
counts mismatches equally; our score weights them by the query magnitudes.

\subsection{From text to an index, then back to results}
The collection contains $N$ documents. Before queries arrive, we embed the text, choose the
representation width $d$, pack the document signs, and build the index. Each document receives
one cluster assignment. A cluster is simply a stored subset of the collection. The index may
learn clusters from vectors, or assign documents from a fixed sign prefix.

Matryoshka training makes selected prefixes useful at smaller dimensions \cite{mrl}. It does
not sort the coordinates of each query by magnitude, and it does not guarantee that 24 sign
bits preserve its nearest neighbors. Truncating an embedding and taking its signs are separate
changes to the representation. Our primary comparison fixes the representation across methods.

At query time, we embed and normalize the query, select clusters, and search their documents.
Opening a cluster is one \emph{probe}. With $C$ clusters and $P$ probes, balanced clusters would
contain about $NP/C$ selected documents. Real clusters need not be balanced, so the actual
count is the sum of the selected cluster sizes. Setting $C=P=1$ searches the whole collection.

\fig{shared}{The common query flow. The three local search methods share the same query and selected clusters when we isolate their work. Longer-vector reranking is optional; it is excluded from the primary binary-score comparison.}{.68}

A production pipeline can apply document filters and rerank candidates with longer vectors or
another model. These stages belong in a complete request measurement when enabled. In this
study, the primary index comparisons use cached query embeddings, the same binary score, and
no float reranker. Later we measure actual text queries as complete requests.

Exa's published vector-database description motivates the cluster-and-scan design and compact
scoring \cite{exa}. Our A is a local baseline with that broad structure. It is not a reproduction
or benchmark of Exa's production system. In particular, sign-prefix routing and learned IVF
clusters are different choices; a $k$-bit prefix defines up to $2^k$ patterns, not $k$ clusters.
