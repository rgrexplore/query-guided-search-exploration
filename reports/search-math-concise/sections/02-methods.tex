\section{Three ways to search the selected documents}
\subsection{A: cluster, then full scan}
Let's first scan the example so we have a result we can check. Coordinate 1 defines our two
clusters; opening cluster 1 and then cluster 0 gives us documents 2, 3, 4, followed by 0, 1, 5.
We calculate each full score and keep the best two. If we visit the documents in another order,
the final ranking is still the same.

We can keep those results in a \emph{top-$K$ heap}: it holds the best $K$ found so far, with
the worst retained result ready to replace. Follow the example with $K=2$. After documents 2
and 3, the retained scores are 0.1 and 2.5; when document 4 scores 1.9, it replaces document 2.
The remaining documents don't improve that pair, so we finish with the reference answer.

\begin{lstlisting}[caption={Full scan. Every selected document receives a full score.}]
scan(query, selected_clusters, K):
    table = prepare_score_table(query)
    best = empty_top_k(K)
    for cluster in selected_clusters:
        for document in cluster.documents:
            score = full_score(table, document.code)
            best.offer(score, document.id)
    return best.sorted_by_score_then_id()
\end{lstlisting}

If we inspect \texttt{full\_score}, we don't need a separate multiplication for every sign.
For each group of four coordinates, we can precompute the contributions of all 16 possible
sign patterns and put them in a score table. A 256-bit document then needs 64 table terms.
There is still work in a lookup: read the bits, extract the pattern, load its value, and add
it to the score. Counting one table term therefore isn't counting one CPU instruction.

With $g$ coordinates per group, the same idea gives $G=\ceil{d/g}$ groups and $G2^g$ stored
table values, allowing padding in the last group. We prepare the table for each query, and
all three methods use it. If we increase $g$, we trade a larger table for fewer terms per
document. The measured implementation uses $g=4$.

Let $\mathcal P$ be the selected clusters and $n_c$ the size of cluster $c$. A scores
\[
F_A=\sum_{c\in\mathcal P}n_c
\]
documents and evaluates $G F_A$ table terms. A useful local time model is
\begin{equation}
T_A^{\rm local}\approx T_{\rm table}+F_Ac_{\rm scan}+T_{\rm select}(F_A,K).
\label{eq:scan-time}
\end{equation}
Here $c_{\rm scan}$ is the time spent reading and scoring one contiguous document at the
chosen width. We have written selection separately so its cost stays visible. If we use a
measured per-row coefficient that already includes selection, we shouldn't add that cost
again. The heap has a worst-case bound of $O(F_A\log K)$, although many scores leave it unchanged.

\subsection{The scan's storage and temporary memory}
Now let's look at what we store. If a packed word has $w$ bits, it takes $u=w/8$ bytes, and
a code needs $u\ceil{d/w}$ bytes. We also need the document ID; call its width $b_{\rm id}$.
Adding those two parts for every document gives
\begin{equation}
M_{\rm rows}=N\left(u\ceil{d/w}+b_{\rm id}\right).
\label{eq:rows}
\end{equation}
For $d=256$, $w=64$, and eight-byte IDs, that is $32+8=40$ bytes per row, or 40 MB for one
million rows in decimal units. We still need to account for cluster directories, spare vector
capacity, and allocator bookkeeping; the row payload doesn't include them.

Routing adds storage and query work too. For example, $C$ float centroids of width $d_r$ need
$4Cd_r$ bytes for their coordinates. If we compare every centroid exactly, each query examines
$Cd_r$ coordinates and then chooses the best $P$ centroids. A sign-prefix router does different
work, so we can't give routing one price without specifying how it is implemented.

During the query, we also keep the query vector, score table, selected cluster IDs, and current
results in memory. Call this shared temporary allocation $Q_0$; its main terms scale as
$O(d+G2^g+P+K)$. If Python and native result arrays coexist, both need to be counted. We can
then add $Q_0$ to the stored rows, routing, and container allocation to estimate A's serving
memory. Building the index can peak higher because the input arrays and newly arranged index
exist together. This is why file size, logical payload, and process RAM need separate counts.

Also, if we look at how the CPU reads the scan's data, the codes in a cluster sit consecutively.
The CPU can fetch future cache lines while working on the current ones, and SIMD instructions
can process several values together. Neither changes the number of documents we score, but
both can change the time per row. So even before introducing another method, we have a reason
to be careful about predicting latency from arithmetic alone.

\subsection{B: arrange the same bits by coordinate}
The query tells us which sign it prefers at each coordinate. One thing we can try is selecting
documents through that sign before calculating their full scores. For this, B stores a
\emph{bitplane}: one coordinate across all documents in a cluster, with the sign data arranged
as columns. We also keep the packed document rows, because selected candidates still need the
same full score as A.

Consider cluster 1 in the example, where the local document order is [2, 3, 4] and the codes
are \texttt{10100}, \texttt{11001}, and \texttt{11000}. If we read coordinate 2 down those
rows, we get plane \texttt{011}: documents 3 and 4 have that bit set. Coordinate 3 gives
\texttt{100}. The query prefers 1 at coordinate 2 and 0 at coordinate 3, so either selection
keeps documents 3 and 4.

We can record the remaining local positions in a candidate mask. Starting with parent mask
$A$ and plane $B_i$, a positive-query split keeps the matching positions in one child and the
others in another:
\[
A_{\rm match}=A\mathbin{\&}B_i,
\qquad A_{\rm other}=A\mathbin{\&}\neg B_i.
\]
If the query coordinate is negative, we swap which child is the match. Both results are
intersected with the parent, so padding positions can't become real documents.

\subsection{Follow the promising branch, keep the alternative}
If we order the query coordinates by magnitude, we get 1, 4, 2, 3, 5. In cluster 1,
coordinate 1 is already fixed, and all three documents match the query at coordinate 4.
The split on coordinate 2 then gives [3, 4] in one child and [2] in the other. Matching adds
no penalty, while the other child adds 0.5, so we try the matching child first.

Trying that child first doesn't mean we can discard the other one. A document could match
this bit and then disagree on several later bits. Instead, we keep unexplored children in
a queue, ordered by a lower bound on mismatch penalty. Equation~\ref{eq:score} gives a node
with known penalty $p$ a score upper bound of $Q-2p$, allowing every unexamined coordinate
its best sign. If even that upper bound falls strictly below the worst retained top-$K$ score,
the node can't improve the result. Equal-score possibilities still need the ID tie rule, and
the native check stays conservative around floating-point comparisons.

\begin{lstlisting}[caption={Bitplane search. The queue preserves alternatives to the preferred path.}]
branch(query, clusters, K, leaf_size, node_budget):
    table = prepare_score_table(query)
    order = coordinates_by_decreasing_abs(query)
    queue = one full candidate mask per selected cluster
    best = empty_top_k(K)
    while queue is not empty:
        node = remove_lowest_penalty(queue)
        if cannot_improve(node, query, best): continue
        if node_budget_is_reached(): return best
        if node.count <= leaf_size or no_bits_remain(node):
            score_each_set_document(table, node.mask, best)
        else:
            matching, other = split_on_next_bit(node, order)
            queue_nonempty_children(queue, matching, other)
    return best.sorted_by_score_then_id()
\end{lstlisting}

The listing gives us the search policy; counters, ownership, and numerical tolerance live in
the native source. Once a node is small enough, we treat it as a leaf and score its documents
directly. The leaf size $L$ tells us when to make that switch. A node budget gives us another
way to stop, but it can end the search before the bounds establish the answer. With no work
limit and safe bounds, we can finish exactly within the selected clusters. We still haven't
made any guarantee about clusters we didn't probe.

We can also occasionally choose another queued node instead of the one with the best bound,
using a probability parameter. This changes the exploration order, not the score. Under a
fixed budget it could help or hurt recall, so it needs seeded tests rather than an assumed
gain. The tested real-data settings didn't show a consistent benefit from random exploration.

\subsection{Count the full-width work}
For cluster $c$, each dense mask spans $W_c=\ceil{n_c/w}$ words. Let $J_c$ count its splits
and $E_c$ the leaf masks whose set bits are enumerated. The full-width visits are
\begin{equation}
V_{\rm split}=\sum_{c\in\mathcal P}J_cW_c,
\qquad V_{\rm leaf}=\sum_{c\in\mathcal P}E_cW_c.
\label{eq:visits}
\end{equation}
Even at a leaf, the loop checks zero words to find out that they are empty, and then the set
bits tell us which documents to score. If we count only the surviving documents, we miss that
first part of the work. An early cost estimate was too optimistic for exactly this reason:
it omitted the leaf-word visits.

Let's follow the larger mask example. We start with 6,400 documents and narrow the candidates
to 80, but the mask still contains 100 words. If we make ten more dense splits, those loops
visit 1,000 words even if only a few bits remain set. Each visit reads the parent and plane,
constructs children, and writes results; we also spend time allocating masks and maintaining
the queue. These costs remain even when the candidate count looks small.

If $F_B$ documents are eventually scored, a practical decomposition is
\begin{equation}
\begin{split}
T_B^{\rm local}\approx{}&T_{\rm table}+T_{\rm order}
 +V_{\rm split}c_{\rm split}+V_{\rm leaf}c_{\rm leaf}\\
 &+F_Bc_{\rm gather}+T_{\rm queue}+T_{\rm select}(F_B,K).
\end{split}
\label{eq:branch-time}
\end{equation}
To use this equation, we need to know what each measured price includes. The split price
should cover the chosen mask allocation policy, and scattered row reads may cost more than
contiguous scan reads. If a leaf timer already covers finding set bits, fetching the rows,
and scoring them, we can use that combined measurement. Adding those same stages separately
would count them twice.

B's additional stored plane payload is
\begin{equation}
M_{\rm planes}=du\sum_{c=1}^{C}\ceil{n_c/w}.
\label{eq:planes}
\end{equation}
For one large cluster, this is approximately $Nd/8$ bytes. If we use many small clusters,
padding adds more. We also need to count the masks waiting during a query: if $A_c(t)$ masks
for cluster $c$ coexist at time $t$, their payload peaks at
$u\max_t\sum_c A_c(t)W_c$. Queue-node allocation and shared scratch come on top of that.
Counting only the mask we're visiting would leave out the alternatives still in the queue.

\subsection{C: begin with the query's key}
There's another way to use the query's preferred signs. Instead of choosing a sequence of
columns as B does, we can build a directory over a fixed set of $h$ coordinates. C stores
documents with the same short key together within each cluster, and the directory gives the
start position and count of each occupied key. The document IDs already identify the posting
range, so this implementation doesn't add a second ID array for postings.

Let's use coordinates 2 and 3 as the key in the same example. The query wants \texttt{10}.
If we flip coordinate 3, the penalty is 0.4; flipping coordinate 2 costs 0.5, and flipping
both costs 0.9. That gives us the weighted order \texttt{10}, \texttt{11}, \texttt{00},
\texttt{01} to try in the directory.

\fig{keys}{One shared key sequence is looked up in both selected clusters. The ideal key already finds the top two, but that fact alone is not a safe stopping rule. Empty lookups still cost work.}{.98}

The first key returns document 0 from cluster 0 and documents 3 and 4 from cluster 1. We
score them fully and get 1.1, 2.5, and 1.9, leaving [3, 4] as the best pair. Can the next key
improve it? Its known penalty is 0.4, so even its full-score upper bound is only
$2.5-2(0.4)=1.7$, below 1.9. Here that bound lets us stop before the empty \texttt{11}
lookups. Figure~\ref{fig:keys} includes the wider sequence to show the directory and its empty
keys; a walk without the bound or a work limit would inspect them too.

It would be tempting to stop as soon as we find $K$ documents, but the short key hasn't checked
the other coordinates. A matching document might score poorly on them, while another key
contains a better full score. We therefore score the full code and keep an upper bound for
unvisited keys, rather than treating the candidate count as proof that we've finished.

\Needspace{25\baselineskip}
\begin{lstlisting}[caption={Weighted key lookup. Generate the key sequence once; charge every cluster lookup.}]
keys(query, clusters, K, candidate_target, lookup_limit):
    table = prepare_score_table(query)
    ideal = signs_of_fixed_key_coordinates(query)
    queue = [empty_flip_set_with_zero_penalty]
    best = empty_top_k(K)
    while queue is not empty:
        if remaining_bound_cannot_improve(queue, query, best): break
        state = remove_lowest_penalty(queue)
        key = ideal XOR state.flip_mask
        for cluster in clusters:
            if lookup_limit_is_reached(): return best
            count_one_lookup_including_misses()
            for document in cluster.directory.get(key, []):
                best.offer(full_score(table, document.code), document.id)
        if candidate_target_is_reached(): return best
        add_next_unique_flip_sets(queue, state)
    return best.sorted_by_score_then_id()
\end{lstlisting}

If we follow the queue, it tries combinations in increasing total mismatch weight. That is
different from simply increasing the number of flipped bits: two low-weight flips may cost
less than one high-weight flip. The native subset-generation rule avoids generating the same
combination repeatedly. For an unvisited key, $Q-2p_{\rm key}$ remains a safe full-score upper
bound because all omitted coordinates could match, although that allowance can make it loose.

We can limit the work with a positive candidate target or lookup limit; zero disables a limit
in the native API. Either limit can stop early and lose recall. The target is checked after a
key has been processed across all selected clusters, while the lookup limit can stop during
that loop. To finish exactly within the selected clusters, we must instead exhaust potentially
improving keys or prove that none remain, with score ties handled consistently.

\subsection{What the key directory costs}
Let $H$ count actual directory lookups and $F_C$ the full scores. With $E$ generated keys and
no limit cutting a cluster loop, $H=PE$. An empty key contributes to $H$ but not $F_C$. A time
model for the implemented policy is
\begin{equation}
\begin{split}
T_C^{\rm local}\approx{}&T_{\rm table}+T_{\rm key\ order}+T_{\rm key\ queue}
 +Hc_{\rm lookup}\\
 &+F_Cc_{\rm posting}+T_{\rm select}(F_C,K).
\end{split}
\label{eq:key-time}
\end{equation}
Rows within a posting range are contiguous, but reading many short ranges can still cost
something different from one long scan. The queue cost also depends on how many generated
states remain live. Since this implementation shares one stream across clusters, we charge
that queue once, not $P$ times.

For $U_c$ occupied keys in cluster $c$, the logical directory payload is
$\sum_c U_c(b_k+2b_o)$: a key, start, and count. The current key field uses four bytes and each
range field uses eight. Allocated memory is larger. The C++ directory uses separate chaining,
with one node per occupied entry and a bucket-pointer array. If $B_c$ is the number of hash
buckets, its allocation includes $\sum_c(U_cb_{\rm node}+B_cb_{\rm ptr})$, plus container and
allocator overhead. The 20-byte field sum is not an allocated-node measurement.

If we widen the key, posting ranges may get shorter, but useful keys may also take more work
to reach. A very short key has the opposite problem: it finds documents easily while leaving
nearly all the scoring work. So finding a nonempty key isn't the same as finding the best
documents. And if we want to relax a pattern to something like \texttt{1*0}, we need a different
operation; an exact-key hash table doesn't answer that wildcard request in one lookup.
